# Shared request protection and guard recovery

Decision for [ticket #11](https://github.com/Anoushka004/car-dealership-inventory/issues/11), 2026-10-25. This is an implementable design prerequisite, not application code or executed runtime evidence. It selects technical mechanisms under the [V1 specification](https://github.com/Anoushka004/car-dealership-inventory/issues/8) and [delivery blueprint](https://github.com/Anoushka004/car-dealership-inventory/issues/10#issuecomment-6396998623). The [canonical REST contract](https://github.com/Anoushka004/car-dealership-inventory/issues/5#issuecomment-6394771175), including its Stock amendment, governs all observable behavior. No new API status, error code, endpoint, or product rule is introduced here.

## Selected mechanism and boundary

Use PostgreSQL 17 in the existing application database for token buckets and operation guards. Local development and CI use their isolated PostgreSQL instance; deployment uses the selected Neon database through its pooled runtime connection. Add no Redis service, paid plan, account, or separate network dependency. Shared PostgreSQL gives all workers one authoritative admission state and transactional locks. This is an implementation selection for the personal learning demo, not a capacity guarantee: protection traffic consumes database connections, writes and free-tier quota.

Use two separate phases: a short, committed protection-admission transaction, then the endpoint's own work. Guarded authentication has an additional short bootstrap transaction followed by one transaction holding the guard through its protected work. An endpoint rollback, invalid credential, failed send, or guard conflict never refunds already committed admission tokens. Ordinary browsing does not take operation guards; its admission briefly serializes only requests touching the same bucket rows.

Keep the implementation boundary small: an immutable budget registry, canonical identity derivation, one atomic `admit(required_buckets)` operation, the special forgot-password sequence, and a guarded-operation transaction wrapper. Return internal admission results (allowed or denied with retry seconds); endpoint serializers retain the approved JSON envelope. Do not expose bucket internals, identity hashes, SQL errors, or guard owners through the API.

## Identity and stored state

Every bucket primary key is `(environment_namespace, group, owner_kind, owner_digest)`. Guard keys use the same namespace plus `operation_kind` and `owner_digest`, in a separate table. Use stable group names from the registry below; request path strings do not create new buckets. Customer/Admin identity always comes from validated access credentials, never a caller-supplied account ID. The shared IP group for refresh/logout/logout-everywhere is one group across all three paths.

Derive digests with HMAC-SHA-256 and a dedicated high-entropy server-side `PROTECTION_ID_KEY`, using an unambiguous length-prefixed encoding of namespace, identity domain and canonical identifier. Separate the HMAC domains for email, IP, account, session and reset-token identities. The group/operation columns isolate workloads; a reset guard digest cannot be used as a refresh lookup verifier. All workers for one environment use the same key and namespace. Preview, test and demo databases/configuration are isolated. Secrets never enter browser bundles.

- Email: trim and lowercase exactly as account normalization does; use the resulting address even when no account exists. Validate syntax first. Do not store the address in protection tables or logs.
- IP: use the trusted and normalized address described below, without a port. Normalize IPv4-mapped IPv6 consistently to IPv4 so textual aliases cannot split one owner. Do not aggregate unrelated IPv6 addresses into an invented network owner.
- Account: authenticated stable account UUID, encoded canonically.
- Session: stable server-side refresh session/family UUID, unchanged by refresh rotation. Look up an opaque token through its dedicated authentication verifier, retaining old verifier-to-family mappings for replay detection through the family's maximum validity window. A caller-selected cookie string or unverified UUID is not a trusted session identity. Different device sessions remain distinct.
- Reset guard: HMAC the exact submitted, syntactically valid opaque reset token under the reset domain, before token lookup. Never persist the raw token in the guard table. Unknown well-formed reset tokens use the same derivation and eventually receive the existing `400 invalid_reset_token`.

For refresh/logout, bounded parsing and an indexed verifier-to-session mapping lookup are part of admission identity resolution; perform no password hashing, rotation, revocation or email work there. Missing or unrecognizable cookies have no identifiable session bucket: apply their IP protection, then preserve `401 invalid_refresh_token` with cookie clearing for refresh and idempotent `204` logout. A recognized old token still maps to its original session for its budget and guard; replay revocation happens after obtaining the refresh guard and revalidating state. Never create an unlimited family of caller-selected session buckets. Reset has an IP bucket and a token guard, not an unapproved token bucket.

`protection_bucket` stores the key, `credit_us bigint`, `last_refill_us bigint`, and the immutable registry parameters `capacity` and `interval_us` or a validated reference to those parameters. Constrain credit to `[0, capacity * interval_us]`, capacity/interval to positive supported bounds, and key values to the registry. Do not silently accept an existing row with incompatible parameters. `operation_guard` stores only its unique key and creation metadata; its row lock, not a mutable `busy` boolean, represents ownership. Store no password, JWT, refresh token, reset token, raw IP or email in either table. Operational logs use request correlation IDs and error categories rather than owner digests.

## Budget registry

Each request costs one token. The interval is the exact microseconds needed to earn one token; this represents every approved refill rate without floating point. Capacities and owner groups below reproduce the canonical contract.

| Group | Capacity | Interval per token | Owner |
| --- | ---: | ---: | --- |
| Public listing/search/detail | 60 | 1,000,000 us | IP |
| `/me` and Customer order reads | 120 | 500,000 us | Account |
| Customer purchase/cancellation | 10 | 6,000,000 us | Account |
| Admin inventory/order reads | 120 | 500,000 us | Account |
| Admin inventory/order mutations | 30 | 2,000,000 us | Account |
| Login | 5 | 180,000,000 us | Normalized email |
| Login additional protection | 30 | 30,000,000 us | IP |
| Registration | 10 | 360,000,000 us | IP |
| Forgot-password delivery | 3 | 1,200,000,000 us | Normalized email |
| Forgot-password requests | 20 | 180,000,000 us | IP |
| Reset-password | 10 | 90,000,000 us | IP |
| Refresh | 60 | 1,000,000 us | Session |
| Logout | 10 | 6,000,000 us | Session, when identifiable |
| Logout-everywhere | 5 | 180,000,000 us | Account |
| Refresh/logout/logout-everywhere additional protection | 60 | 1,000,000 us | IP, shared across those routes |

Static vehicle metadata, static assets and basic process health remain exempt. Database readiness is internal/restricted or explicitly protected; it cannot become a public unbudgeted database probe. Any genuinely new expensive operation requires an explicit budget rather than borrowing an unrelated group's allowance.

## Atomic admission and exact refill

The application uses one synchronous Django/psycopg transaction on its owning thread. Do not hold an admission transaction during endpoint work. Deduplicate required keys, sort the full keys lexicographically, and acquire them in that order in every code path. At `READ COMMITTED`, for each key insert a full bucket with `INSERT ... ON CONFLICT DO NOTHING`, then fetch it with `SELECT ... FOR UPDATE`; existing rows are never reset by the insert. Keep all these row locks until the admission decision commits. The unique key resolves concurrent first use; bootstrap races must not create independent full allowances. Use the same deterministic order for insertion and locking to prevent opposite-order deadlocks.

After all required rows are locked, sample PostgreSQL `clock_timestamp()` once and convert its epoch to integer microseconds using numeric arithmetic, never a floating-point application clock. For each row let `C` be capacity, `I` the token interval in microseconds, `B` stored credit, `L` the last refill timestamp, and `T` the sampled time:

```text
effective_time = max(T, L)
elapsed = min(C * I, effective_time - L)
refilled_credit = min(C * I, B + elapsed)
can_admit = refilled_credit >= I
```

Use checked integer/numeric intermediate arithmetic before storing bounded bigint values. The interval registry's largest initial balance is 3,600,000,000 microseconds. Preserve fractional tokens as credit: no request-time rounding or loss of sub-token remainder. If the database clock moves backward, clamp time to `L`; do not add negative credit or move the timestamp backward. No application worker's clock participates in production admission. A sustained database clock fault is an operator incident, not permission to clear state.

If every bucket can admit, subtract `I` from each refilled balance, update every timestamp to its effective time and commit all debits together. Otherwise debit none. It is permissible to persist the computed refill and timestamps on a denial, but no bucket loses a token. Missing buckets start full; successful requests never add credit beyond time refill. A guard conflict, wrong password or failed endpoint later does not change these committed balances.

For a denial compute, using the same locked snapshot, each `wait_us = max(0, I - refilled_credit)`, then `Retry-After = ceil(max(wait_us) / 1,000,000)` as a positive whole number. If the database clock moved backward and a bucket is deficient, also add `max(0, L - T)` to that bucket's wait: refill cannot resume until its stored time is reached. Return the approved `429 rate_limited` envelope and decimal header. This is the first admission opportunity in the absence of new competing consumption, not a reservation. Do not return an authoritative IP-only denial for a multi-bucket route: a slower depleted email/session/account bucket might require a larger value. An IP availability probe may be non-debiting, but the final decision and maximum wait still inspect every applicable bucket. No pre-debit-and-refund scheme is allowed outside the explicit forgot-password exception.

Login computes both IP/email identities from validated input and performs the combined admission before account lookup or Argon2id. Refresh/logout need the bounded indexed identity lookup described above to know all applicable keys, including when the IP bucket is empty; this lookup is part of protection admission, not credential acceptance. Protect request size/token format before it, and do no expensive authentication work until admission commits. Logout-everywhere validates the bearer token cryptographically before account-owned admission; all three cookie/session routes share their additional IP bucket. Other account-owned routes similarly validate bearer syntax/signature/claims before deriving an owner.

## Forgot-password suppression

Forgot-password deliberately uses two committed admission decisions, in this order:

1. Validate email syntax. Enforce and debit the IP request bucket. If empty, return `429 rate_limited` with its rounded-up `Retry-After`; do no account lookup or send.
2. Enforce the normalized-email delivery bucket, including for nonexistent accounts. If empty, debit no email token, perform no account lookup/reset-token mutation/send, and return the same ordinary `202` neutral message. Keep the IP debit.
3. If an email token is available, commit that debit before looking up the account. For a known account issue the new single-use reset token atomically, invalidate its older tokens, then attempt the configured SMTP delivery synchronously. For an unknown account do no send. Provider failure and suppressed sends retain the same `202` response and do not refund either bucket.

The same path, budgets and outward message apply to all syntactically valid addresses. Do not introduce a response header or message exposing email suppression/account membership. Protection SQL touches only protection state before suppression, not account or reset-token tables. Test instrumentation must distinguish protection queries from forbidden account queries. Never send a link until its token persistence commits. If database token issuance has an uncertain outcome, do not send an unconfirmed token; record an operator-safe failure and retain the neutral admitted-request response.

## Guard ownership, recovery and timeout

Login, refresh and reset use one shared guard each: login by normalized email, refresh by stable session, reset by reset-token digest. They are separate from token buckets. Only after admission commits, ensure the guard row exists in its own short transaction and commit that bootstrap before starting the guarded transaction. A first-ever guard must be committed before anyone owns it: inserting it inside the protected transaction can make an overlapping insertion wait until the operation ends and miss the required conflict.

Begin the guarded transaction, set transaction-local timeouts, then acquire the existing row with `SELECT ... FOR UPDATE NOWAIT`. A lock conflict specifically from this guard-acquisition statement returns the existing `409 request_in_progress`. Roll back that transaction; admission remains spent. Do not map an unrelated lock timeout/deadlock/database error to a fictitious guard conflict. Different keys do not conflict. Neither process-local mutexes nor session-scoped advisory locks implement this guarantee.

The PostgreSQL transaction owns the lock. Retain it while performing the operation's reads, Argon2id check/hash (including dummy verification for nonexistent login), state revalidation, session/token changes, and success-result construction/signing. Refresh revalidates the submitted verifier *after* taking its family guard: another worker's successful rotation must not be accepted from a stale pre-admission lookup. Reset revalidates token eligibility and locks the account/reset records needed to handle supersession and revocation. Serialize the response representation and construct credentials while still guarded; emit the success response/cookie only after a confirmed commit. Expected authentication failures may commit necessary state, such as replay-family revocation, before emitting their approved error. Do not accidentally roll back revocation by raising an HTTP exception inside the transaction.

Commit/rollback releases the guard automatically; no lease renewal, unlock RPC or crash-cleanup boolean is required. After a killed worker, PostgreSQL releases it when the connection ends. For a stopped, partitioned or orphaned client, bound the transaction with PostgreSQL 17 `transaction_timeout`, supported and verified on the actual selected connection. Initial design values are a 20-second transaction timeout, 15-second application deadline, 10-second idle-in-transaction timeout and 5-second statement timeout. All are transaction-local; the foundation must measure the real configured Argon2id workload and prove these values fit normal operation on the pinned runtime. A later measured adjustment must keep a finite guard lifetime below the configured function request budget. The idle timeout must exceed the measured longest off-database hash/sign step, and a statement timeout alone is insufficient for a worker that stops between statements.

Timeout terminates or aborts the old database transaction before a new worker can own the row. The old operation is terminal: discard pending credentials/results, close its connection, and return only an existing sanitized failure if the response channel still exists. Never reconnect and continue/retry the old guarded work, or emit success after losing transaction ownership. No external side effect occurs inside these three guarded operations before their confirmed commit. A suspended CPU computation may finish after cancellation, but its result cannot mutate state or become an authentication response. There is no time-based stealing of an apparently expired row that leaves a live old transaction authorized to commit.

Guard acquisition protects the operation through durable result creation, not network transmission of its response: the server cannot hold a transaction until a browser acknowledges receipt. A later request after commit is evaluated against current token/session state and canonical replay rules. This does not relax cross-tab refresh serialization.

## Error precedence and outages

Reject malformed body/header syntax, invalid bearer credentials and rejected Origin/CSRF checks before database work where possible, with existing `422`, `401` and `403` codes. Valid protected requests then establish their identities, atomically admit all applicable budgets (or follow forgot-password's exception), acquire any guard, and perform endpoint work. Rate exhaustion precedes a guard attempt; a guard overlap consumes the already admitted token(s). Revalidate mutable credentials/domain state under the appropriate transaction before acting. This sequence does not change inventory version/capacity or Order transition precedence.

If protection state, database connectivity, required configuration or trusted client identity is unavailable, do not fall back to in-process buckets, unguarded work, empty query results or optimistic success. Return the existing sanitized `500 internal_error`; do not invent `503`, a new error code or a `Retry-After` suggesting actual rate exhaustion. This includes forgot-password when its IP/email admission cannot be established: a neutral success fallback would bypass required protection. Once forgot-password's protection decisions are committed, account lookup/token-issuance/SMTP failures retain the same neutral `202` for privacy and skip any unsafe send; log an operator-safe category and alert through the configured mechanism. Static/exempt responses may remain available.

Loss of the admission COMMIT acknowledgement is an uncertain outcome: do no endpoint work, make no automatic debit retry or refund, and fail safely. PostgreSQL might have committed the debit. A fresh client request is a fresh protected attempt. A lost guarded-operation commit acknowledgement similarly cannot justify replaying credentials or mutation; the endpoint's existing retry/replay policy determines recovery. Protection is not purchase idempotency.

Log dependency/timeout/configuration failures separately from actual exhaustion and guard conflict, without credentials, raw identities, SQL parameter dumps or full reset URLs. A worker restart, deployment, database reconnect or recovery must reuse persisted balances and stable identity configuration; it cannot grant a fresh allowance to every owner. Service restoration resumes normal refill using database time, capped at capacity.

## Trusted IP and deployment lifecycle

Use the already selected topology: in direct/local HTTP mode ignore all forwarded headers and use the socket peer. In Vercel mode only, parse the platform-overwritten `x-forwarded-for` as exactly one valid normalized IPv4/IPv6 address. Do not choose a caller-selected first/last member of a chain; ignore `Forwarded`, `x-real-ip` and geo headers as alternatives. Missing/invalid trusted platform IP is a configuration failure with existing `500 internal_error`. No external proxy is part of this topology. Verify spoofed headers are overwritten on the actual deployed route before release.

Foundation supplies Django migrations for the protection tables and constraints alongside application schema work, a least-privilege runtime role, and transaction-local settings with same-thread connection cleanup. Use `CONN_MAX_AGE=0`, disable server-side cursors under transaction pooling, and keep privileged migration credentials separate. The managed pool pins a backend while a transaction is active, so the guard uses transactional row locks; no session-affine feature is required. A guard holds a pooled backend during its transaction, including hashing. Verify bounded concurrency, Argon2id memory and connection demand within the actual free plan instead of increasing resources automatically.

No new service appears in Compose: PostgreSQL and Mailpit remain the local dependencies. The existing planned `docker compose up -d --wait postgres mailpit`, migration and two-worker API test commands remain the lifecycle contract. PostgreSQL has an isolated persistent development volume and disposable CI/test databases; no test consumes the demo database or Neon quota. Migrations use the direct connection and controlled release workflow from the blueprint. Do not run migrations or erase state during an API request/build.

Keep initial V1 guard rows and bucket rows persistent; do not run concurrent expiry/deletion jobs. This avoids an old and replacement guard row permitting two owners, and avoids a maintenance lock masquerading as `request_in_progress`. Monitor table/index size, connection occupancy, lock duration and quota headroom; alert before limits. If storage quota is reached, stop protected work with existing safe errors rather than evicting live protection state. This bounded demo accepts the storage cost of retained pseudonymous identifiers; they are not claimed to expire automatically.

Optional owner-operated retention maintenance requires disabling *all* API admission, draining every worker and verifying no active request transaction remains. Abort maintenance if draining cannot be established. With no API workers active, unused guard rows may be removed; bucket rows may be removed only when their computed balance is full under the current registry, since recreation then grants no extra credit. Preserve depleted buckets and authentication verifier/replay records for their required lifetimes. Resume only with unchanged namespace/key/registry and compatible schema. An online pruning algorithm is future work requiring its own correctness review; TTL is not authorization to delete a live guard.

Do not rotate `PROTECTION_ID_KEY`, change namespace or change existing group parameters during an ordinary rolling deploy: these changes otherwise split identity or reset allowances. A trusted setup command, before workers serve traffic, initializes one database singleton with the expected environment namespace, registry version/digest and `HMAC(key, fixed configuration-check domain/challenge)`. Keep the key out of migrations. Each worker reads and validates this record before serving protected requests; a missing record or mismatch fails closed. Worker startup never auto-registers its own configuration or silently creates a new namespace. Test setup initializes this record in its fresh isolated database. Coordinate any configuration migration with stopped/drained admission and an explicit state-preservation plan; retaining the old protection key until safe migration is preferable to silently granting full buckets. Secret compromise requires an operator incident procedure, not an automatic empty-table reset.

Backup/restore rehearsals include protection state. If exact current balances cannot be recovered after an old snapshot restore or key loss, stop/drain every worker and keep admission disabled for at least the longest full-refill period from the last possible admission: 3,600 seconds for the current registry. If that last time is unknown, start the full wait only after quiescence is proven. All approved buckets would then naturally be full; reinitialization can grant no earlier allowance. Recalculate this bound after any explicitly approved registry change. Database/session/domain recovery must be reconciled separately before reopening, including old tokens and uncertain commits; waiting does not repair those records. No bucket deletion, session deletion or deployment rollback erases successful purchase keys or Order history.

## Reproducible two-worker verification plan

These are required future tests, not checks executed for this design ticket. Implement them at the already approved HTTP-to-real-PostgreSQL seam, using actual protection tables and distinct Uvicorn processes. Test-only controls may coordinate barriers, database-authoritative time and failure injection, but must not exist in deployed routes/configuration. Assertions use HTTP results and observable account/Order/inventory behavior; safe test telemetry may prove negative account-query/send assertions where HTTP alone cannot.

1. Create a fresh isolated PostgreSQL 17 database, apply all migrations, configure one test namespace/key for both workers and local Mailpit, and start workers on separate loopback ports with one shared database. Wait for bounded readiness. Seed approved accounts/options through supported setup interfaces. Pin the locked dependencies and record the command/environment versions.
2. For every registry group, alternate HTTP calls across workers and verify one shared capacity; use a controlled database-time fixture rather than waiting minutes. Check fractional refill (including 2 tokens/second), cap saturation, no successful-request refill, no negative balances and a full allowance on concurrent first use. Exercise explicit backward and forward clock samples: a backward sample neither adds credit nor moves stored time backward, its deficient-bucket `Retry-After` includes clock catch-up, and a forward sample refills only up to capacity. Freeze time for burst assertions so incidental refill cannot hide errors. All production decisions must continue to use PostgreSQL time.
3. Exercise login email+IP, refresh session+IP, logout session+IP and logout-everywhere account+IP with each bucket independently empty and with both empty. Verify none are debited on denial, and a later allowed call can use the preserved allowance. Use literal expected `Retry-After` values at fractional boundaries (for example a 1.2-second deficit gives `2`) and maximum wait across buckets. Verify account, IP, group, session and environment isolation.
4. Exhaust one normalized email from two textual-case variants; prove they share login/forgot state even when nonexistent. Exhaust a forgot email bucket while keeping IP capacity, then prove normal `202`, no account/reset query/send and one consumed IP token. Exhaust its IP bucket and prove `429`. Compare known, unknown, suppressed and SMTP-failure outward messages and headers. Do not expose account existence via suppression telemetry to clients.
5. Hold worker A at a barrier *after acquiring* each login/refresh/reset guard. Send B's same-owner request with available budgets; require immediate `409 request_in_progress` and spent tokens. A different owner remains admitted. Cover the first-ever guard bootstrap race, rotated-token-to-same-session overlap and an unknown reset token. Release A, check normal subsequent invalid/replay/success semantics, and ensure browsing remains concurrent.
6. Kill A while guarded, then retry through B after PostgreSQL observes disconnect: the lock is released and no half-applied state remains. Separately stop A without closing the socket, wait beyond the configured database transaction timeout and verify B can proceed. Resume A and prove it cannot commit or emit credentials. Repeat with database disconnect/connection-pool failure at admission, guarded mutation and commit acknowledgement. Verify no stale reconnection continuation, unguarded fallback or fabricated success.
7. Cover auth failure/replay paths, token revocation and reset supersession under guards. Verify replay revocation actually commits, old verifier mappings preserve family identity, unknown cookies cannot manufacture session budgets, and a failed guarded transaction does not refund admission. Confirm SQL lock timeouts unrelated to guard NOWAIT do not become `409`.
8. Stop/restart each worker and PostgreSQL without clearing its data; balances survive and refill only by elapsed time. Exercise quiesced maintenance with depleted/full buckets and verify no extra allowance. Roll out identical configuration across workers, then make mismatched key/namespace/registry configuration fail startup/configuration validation rather than run split protection silently.
9. In local mode send spoofed forwarding headers and prove identity remains the socket peer. In a later authorized Vercel smoke test verify platform overwrite, exact single-IP parsing, canonical normalization and safe failure for missing/invalid platform identity. Verify pool behavior and transaction-local timeout permissions on actual Neon PostgreSQL 17; release remains blocked if these assumptions fail.
10. Stop the dependency at each forgot-password phase: pre-admission failure yields safe `500`, established IP exhaustion yields actual `429`, established email suppression yields neutral `202`, and post-admission account/token/send failure yields neutral `202` without an unsafe send. Test cheap exemptions independently. Run distinct tests proving purchase idempotency, last-unit ordering and final transitions still depend on their durable domain transactions, not guard expiry.

The runner uses deterministic barriers rather than hoping requests overlap, bounded waits, and `finally` cleanup that terminates both worker process trees and drops only its isolated test database. It must report unavailable services/skipped checks truthfully. Foundation must supply and verify the reproducible PowerShell/CI commands; this record does not claim Docker, PostgreSQL, Mailpit, application routes, migrations or test hooks already exist.
